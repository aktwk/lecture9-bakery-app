Start and use the app

Double-click START BAKERY.bat, or run python app.py --open-browser. Open http://127.0.0.1:8000. Keep the terminal open; Ctrl+C stops the app. A port conflict can be avoided with python app.py --port 8001 --open-browser.

  1. Fetch today's DMs. Messages for the current planning date become visible. Valid changes and cancellations apply to accepted orders immediately, with the result recorded.
  2. Review the plan. New requests show quantities, dates, hours, rule checks and rejection controls. Book a helper before the two-day deadline if extra capacity is worth $100.
  3. Accept all and go to next day. Inspect the confirmation showing which requests fit together. The app accepts eligible new orders one by one, keeps incompatible requests for review, marks today's accepted orders picked up at the simulated 5 PM close, and advances the date.

Use Orders for all accepted/cancelled/picked-up records, Instagram inbox for original messages, Baking plan for other weeks, and Project brief for rules and the activity log. Record a request supports a new order, change or cancellation.

Database and external data

One bakery.db file stores all operational data. Thirteen CSV orders start accepted. All 25 DMs are staged from the seven supplied HTML files; Fetch reveals only messages whose received date has arrived. It is a classroom data feed, not a live Instagram integration.

Database labels: Requested and Incompatible are live classifications of pending requests. Accepted, rejected and pending are request decisions; accepted, cancelled and collected are order states. The interface displays collected as Picked up. This preserves the original message while linking it to the resulting order.

Business rules and assumptions

  • Cupcakes: $40/dozen and 30 oven minutes/dozen; cake: $120 each and 2 hours each. One product per order; whole quantities.
  • Eight oven hours per day. One $100 helper adds four oven hours. All baking happens on pickup day; pickup is at 5 PM.
  • Orders, changes, cancellations and helper bookings require two calendar days' notice. Both receipt and decision date must qualify. Already accepted CSV orders are grandfathered.
  • New orders require the baker's explicit acceptance. Valid changes/cancellations apply on Fetch, following the lecture's transition table.
  • Rejected and cancelled orders do not reserve future oven capacity. Picked-up orders retain their historical hours and sales.
  • Revenue is booked sales, not cash received. Helper-adjusted balance excludes ingredients and other costs and is not profit.
  • Time is simulated. Closing a planning day represents passing that day's 5 PM pickup, independent of the computer's actual clock.

Implementation and verification

app.py contains the parser, fixed rule functions, SQLite transactions, local HTTP server and page. It uses only the Python standard library. Each write uses a transaction; failures leave orders and the planning date unchanged. No AI model is called inside the app.

Run python -m unittest -v test_app.py. The 15-test suite uses temporary database copies, never the live database. It includes repeated Fetch, late updates, sequential capacity conflicts, helper deadlines, pickup transitions, restart persistence and HTTP checks. See the full-week scenario results.

To back up: Project brief → Download database backup. To export: Orders → Export orders. To restore: stop the app, preserve your old file, replace bakery.db with the backup renamed to that name, then restart.
