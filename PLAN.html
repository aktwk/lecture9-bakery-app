Final bakery app: plan before implementation

Based on Lecture 9, pages 19-26. The original app is preserved in initial-build. The final app lives separately in final-build; no live database will be used for testing.

Purpose and interface

Make daily decisions easy: see today's pickups, fetch today's messages, see compatible and incompatible requests beside their reasons, book helpers, reject unwanted requests, then accept all eligible remaining orders and move to the next day.

Daily schedule: accepted orders, used/free oven hours, helper button
Compatible new requests: customer, product, date, current capacity, [Reject]
Incompatible requests: customer, reason, [Details] [Reject]
Changes and cancellations applied by Fetch: result and reason
Activity log and documentation

State model

Unfetched DM --Fetch--> Requested or Incompatible (live rule check)
Requested --explicit Accept / Accept all--> Accepted
Requested or Incompatible --Reject--> Rejected
Accepted --valid fetched change--> Accepted with updated quantity
Accepted --valid fetched cancellation--> Cancelled
Accepted --end of pickup day, 5 PM--> Picked up
Incompatible --capacity freed or helper booked--> Requested (if notice still valid)

Fetch applies valid changes/cancellations in source order, records invalid ones as incompatible, and never accepts a new order automatically. The batch action rechecks every pending new order in received-date/ID order, one at a time. Incompatible new orders remain pending for review rather than becoming accepted or silently rejected.

Code and data

One standard-library app.py: parser/import, SQLite access, fixed rule checks, fetch/decision/day transitions, HTTP JSON endpoints, then the plain HTML/CSS/JavaScript interface. Build and verify these parts in that order.

Daily capacity, hours used, order counts, revenue and costs are derived from these records to avoid contradictory duplicated totals. One day has many orders and at most one helper.

Fixed rules

$40 and 30 minutes per dozen cupcakes; $120 and two hours per cake. Whole quantities, one product per order. Eight oven hours per day; one $100 helper adds four hours. Orders bake only on their pickup day and are picked up at 5 PM. New decisions, changes, cancellations and helper bookings need two calendar days' notice. A change replaces the old quantity and preserves it when invalid.

Verification plan

  1. Use only temporary database copies for unit and HTTP tests.
  2. Verify import counts, repeated Fetch, future-message isolation, notice boundaries and cross-month dates.
  3. Verify sequential batch capacity, helper deadlines, cancellation and change behavior, automatic pickups and persistence after reopening.
  4. Run Monday-Sunday accepting every eligible order each day, both with no helpers and with a Saturday helper booked in time. Record decisions, daily hours, revenue and helper costs.
  5. Review the interface for understandable actions, nearby facts, feedback, consistent status labels and confirmation before advancing the day.
  6. Prepare README.html, a three-sentence comparison and a clean upload package excluding databases, logs, account details and the lecture PDF.

Boundaries

Fetch reads the supplied local Instagram records; it is not a live Instagram connection. Advancing the simulated day represents passing 5 PM on the day being closed and marks its accepted orders picked up. Public GitHub publication is a separate action requiring the user's repository/account choice; document instructions alone are not publication approval.
